# Architecture Overview

## Purpose

This repository automates the browser flow of the Credit Mantra application. It focuses on verifying the product from a user perspective rather than testing individual components in isolation. The goal is to ensure that core customer journeys remain stable as the app evolves.

## Architectural style

The implementation uses the Page Object Model (POM) combined with Playwright's multi-project configuration. This provides a clean separation between:

- test specifications
- UI selectors and actions
- reusable fixtures and data
- environment configuration
- browser-state setup

## Test execution model

At runtime, Playwright loads the configuration from `playwright.config.ts` and creates the following execution flow:

1. `setup` project runs first
2. It logs in as buyer/officer/developer user types
3. Browser storage state is saved into `.auth/*.json`
4. Role-based projects consume those stored sessions
5. Tests run in parallel according to project and file configuration

This pattern avoids repeated login overhead and keeps tests stable when the app enforces session checks.

## Directory responsibilities

### `pages/`

Each page class encapsulates selectors and common interactions for a screen or feature area.

Examples:

- `LoginPage`: login form and auth expectations
- `RegisterPage`: account creation validation and mismatch states
- `UploadPage`: file upload and demo analysis actions
- `CalculatorsPage`: calculator inputs, tabs, and assertions
- `DeveloperPortalPage`: API key and developer dashboard behavior

### `tests/`

This is the executable suite folder. The tests are grouped by user role and feature domain:

- `guest/`: public page/tests
- `auth/`: login/register/password-reset/redirect flows
- `borrower/`: logged-in borrower scenarios
- `developer/`: API contract and role restrictions
- `integration/`: calculator logic validations
- `setup/`: session creation for reuse

### `utils/`

Utilities contain cross-cutting helpers that make the suite robust.

- `rate-limit.ts`: 429 handling and retry logic
- `finance.ts`: calculator logic and formatting helpers
- `env.ts`: environment variable retrieval
- `storage-state.ts`: shared storage path management

### `test-data/`

This folder centralizes data fixtures to keep tests readable and easy to extend.

### `.auth/`

This directory stores cookie/session files generated by the setup project. It is treated as generated state rather than source code.

## Session and role model

The app appears to use authenticated roles with different permitted pages and APIs:

- Borrower: access to borrower flows, upload, dashboard, assistant, results
- Credit Officer / Underwriter: protected officer pages and dashboards
- Developer: API portal, key management, API-based scoring endpoints

The suite enforces this by validating both the UI and API response conditions for each role.

## Safety and resilience practices

The project intentionally includes patterns for flaky live systems:

- page-level retries on auth throttling
- wait logic when the app serves 429 pages with a countdown message
- error handling around login reuse in `beforeEach`
- URL assertions to validate redirects rather than relying solely on DOM text

This makes the suite more resilient when the app behavior is rate-limited or when login state is reused across runs.

## Authentication flow design

Authentication is not just a simple click; it includes a network-aware helper layer:

- `gotoAuth()` ensures the app is on an auth page and handles server-side cooldowns
- `performAuthFlow()` wraps the full login/register flow so a single 429 does not fail the run
- `waitOutRateLimit()` waits until the server-side cooldown expires before retrying

This is one of the most important architectural choices in the project, because the application appears to gate auth pages with a per-IP rate limit.

## Calculator integration logic

The test suite does not just assert that a calculator renders. It also validates real behavior by interacting with DOM values and checking output changes.

Examples include:

- DTI boundary bands
- EMI clamping rules on blur
- tax-month clamping to a max of 12
- SSF warning display and capped value behavior

This ensures the suite covers not only the UI shell but also business rules.

## CI and execution characteristics

The config chooses pragmatic defaults for CI and local runs:

- tests run in parallel
- traces are captured for retries
- screenshots only on failures
- videos retained on failures
- auth flows get longer timeouts because of server throttling

These settings strike a balance between speed and stability.

## Expected maintenance model

Because this is a browser automation project, the most common maintenance tasks are:

- updating selectors when the UI changes
- refreshing expected text values on product changes
- adjusting rate-limit logic if the app's cooldown messaging changes
- updating environment variables for new environments
- extending page objects when a new feature page is introduced

## Summary

The repository follows a pragmatic E2E automation architecture optimized for a live web application with role-based access. It favors reliability, repeatable auth-state reuse, and defensive handling of the app's real-world quirks such as rate limiting and redirect-based logic.
